# Example: client update when the work is just starting

**Context:** Example Client (GrantPoint), 2026-10-26. Email from Rachael to Matt, the executive director, who is not technical. The work was only beginning: a short-term safeguard was done, and the real update hadn't started.

**The lesson:** Rachael rejected the first draft because "it doesn't explain why it takes time or what the benefit is. It sounds like everything is done, but we are just getting started on the update."

## Before (rejected)

```
- Done: the next ten grant cycles, 2027-2028 through 2036-2037, are now set up in GrantPoint...
- In progress: award letters will fill in each cycle's dates on their own...
- In progress: the admin dashboard will show new cycles as they come in...
- In progress: GrantPoint will keep each cycle in one place instead of several...
```

What was wrong:
- It opens with "Done" twice, so the reader takes it as finished work.
- It lists changes with no reason they're needed.
- It never says why the work takes time, so a long timeline later looks like a delay.
- It never says what the client gets out of it.

## After (approved)

```
Subject: Getting GrantPoint ready for future grant cycles

Hi Matt,
I'm starting an update to GrantPoint so it handles each new grant cycle on its own, instead of needing someone to set up each year by hand. Here's what that involves:
- Why it's needed: today, the grant year is stored in several separate places: the application portal, the annual update form, a few behind-the-scenes steps, the admin dashboard, and the award letters. Each one has to be updated by hand for every new cycle, and if one is missed, things break quietly. For example, organizations can't file their annual update, or next year's letters go out with this year's dates.
- What I've done so far: a short-term safeguard. I added the next ten cycles (through 2036-2037) everywhere GrantPoint needs them, so nothing breaks when the 2027-2028 cycle opens on January 1. This year's grants weren't affected.
- What's next: moving all of those places onto one shared list of grant years, so each part of GrantPoint reads the year from the same spot. That includes award letters filling in each cycle's dates on their own, and the dashboard showing new years as they arrive.
- Why it takes some time: each of those places has to be switched over and tested one at a time, on sample records, without disrupting applications, payments, or Sharon's work. The current setup stays in place until each piece is checked, so if anything isn't finished by January 1, the portal keeps working as it does today.
- The benefit: no yearly setup, no out-of-date letter dates, and fewer places for things to go wrong as GrantPoint grows.
Two quick questions:
- Can you confirm the 2027-2028 application window is January 1 to March 31?
- Is there a stretch you'd rather I not make changes, like a payment week?
Let me know if you have any questions, or if there's anything you'd like me to handle differently.
All best,
Rachael
```

## Why it works
- **The first sentence says where the work stands:** "I'm starting an update." The reader can't take it as finished.
- **It explains the problem before the fix,** in the client's terms: the portal, forms, dashboard, and letters, not fields or formulas. It gives one concrete example of what breaks.
- **It separates what's done from what's next,** and calls the done part what it is: a short-term safeguard.
- **"Why it takes some time" is its own bullet.** It names the constraint the client cares about (not disrupting applications, payments, or staff) and the safety net (the current setup stays until each piece is checked).
- **"The benefit" is its own bullet,** in outcomes the client feels: no yearly setup, correct letters, fewer things to break.
- **It ends with two questions** that only the client can answer, then an open invitation.
- **It stays plain:** no field names, IDs, or tool jargon, no em dashes, and no promises it can't keep ("if anything isn't finished by January 1, the portal keeps working").

## Pattern to reuse for "we're starting X" updates
1. One sentence on what you're starting, and the result it'll have for them.
2. Why it's needed: the current problem in their words, with one concrete example.
3. What's done so far, named honestly. If it's a stopgap, call it a stopgap.
4. What's next.
5. Why it takes time: the constraint, plus the safety net.
6. The benefit.
7. One to three questions only the client can answer, then the closing.
